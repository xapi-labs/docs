Each component shows the method, URL, path parameters, query parameters, request body and a send button. Use the
**Production / Test** tabs above an endpoint to switch between `https://sandbox.xapi.to` and
`https://sandbox.test.xapi.to`. Production is selected by default; when you switch on any endpoint,
the other endpoints on this page switch to the same environment.
For endpoints that require authentication, enter the `XAPI-Key` for the selected environment in the component. Don't mix test and production keys.

## End-to-end Sandbox API test flow

<Steps>
  <Step title="Free connectivity check">
    Expand **List offerings** and click **Try it → Send request**. Expect HTTP `200`, and confirm that the target
    offering has `capabilities.exec=true`. This step needs no key and creates no resources.
  </Step>
  <Step title="Get a quote">
    Expand **Get a Sandbox quote**, enter your `XAPI-Key` in the API Explorer, set
    `requirements.capabilities` to `exec, files`, and set
    `maxEstimatedHourlyUsd=0.20`. Expect HTTP `201`; copy `quoteId`,
    `expiresAt` and `estimatedHourlyUsd` from the response. A quote by itself does not create an instance.
  </Step>
  <Step title="Create and save the instance ID">
    Expand **Create a Sandbox instance**, put the `quoteId` from the previous step into `selection.quoteId`, and change
    `idempotencyKey` to a value unique to this test run, for example
    `manual-browser-20260813-001`. Expect HTTP `202`; save the `id` from the response right away.
    At this point `observedState=PROVISIONING` and the instance cannot run tasks yet.
  </Step>
  <Step title="Wait for RUNNING and run the marker">
    Use **Get instance details** to query the same `id` every 2 seconds until `observedState=RUNNING`. Then, in
    **Run a shell command**, run `printf 'MANUAL_TEST_OK=42\n'`. HTTP should be `201`, and
    the response must show both `exitCode=0` and `stdout` containing `MANUAL_TEST_OK=42`.
  </Step>
  <Step title="Terminate whether it succeeded or failed">
    In **Terminate an instance**, enter the same instance `id` and a new action idempotency key. After submitting, keep querying the details until
    `observedState=TERMINATED` or the terminal `FAILED` state. Closing the web page does not terminate the instance.
  </Step>
  <Step title="Check audit, cost and leftovers">
    Query the four audit streams: CREATE/EXEC/TERMINATE in `operations` should have succeeded, `events` should cover
    RUNNING and the terminal state, `usageSegments` should have no open segments, and all `billingPeriods` should be settled.
    Finally, query history with `state=ACTIVE` and confirm that no active instance from this run remains. **List account instances** keeps
    `TERMINATED` / `FAILED` terminal records, so a non-empty list does not mean resources are still running.
  </Step>
</Steps>

<Tip>
  In the API Explorer, enter the key only in the credential field. Never put it in the request body, metadata, screenshots or doc source.
  Check the URL again before sending: the page uses `https://sandbox.xapi.to` by default; switch to
  `https://sandbox.test.xapi.to` only when you are explicitly running test acceptance. Both environments request real provider resources and incur real charges.
</Tip>

### One-command acceptance with the new local CLI

If you just want the fastest check of the real path, run the new, not-yet-released CLI from local source. It runs
`quote → create → wait → exec → terminate → cost` automatically:

```bash
cd /Users/daxiongya/Desktop/Projects/web3/x402/bsc/xapi-workspace/xapi-cli
npm run build

node dist/index.js sandbox run \
  --host sandbox.xapi.to \
  --capabilities exec,files \
  --max-hourly-usd 0.20 \
  --command 'printf "MANUAL_TEST_OK=42\n"' \
  --format pretty
```

On a pass, check for: `readyState=RUNNING`, `result.exitCode=0`, the marker in `stdout`,
`cleanup.state=TERMINATED` and `finalState=TERMINATED`, and record the `totalCost` returned by the server.

## Execution and artifacts

### Run a shell command

A successful HTTP response does not mean the command succeeded; you must also check `exitCode=0`.

To start a long-running process such as a web server, first confirm that the Offering returns
`capabilities.backgroundExec=true`, then pass `background=true`. This creates a provider-managed background session;
don't enable it for ordinary commands. A background response only proves the session was accepted; you still need to poll the app's health URL to confirm the service is actually ready.

## Completion criteria

<Steps>
  <Step title="Business result passes">
    HTTP status codes are correct; the shell command also shows `exitCode=0`; files and public URLs contain the expected artifacts.
  </Step>
  <Step title="Instance reaches a terminal state">
    After terminating, keep querying until `observedState=TERMINATED` or the provider's terminal `FAILED` state.
  </Step>
  <Step title="Audit and cost are complete">
    Operations, events, usage segments and billing periods can all be queried; cost uses the server's `totalCost`.
  </Step>
  <Step title="No resources left behind">
    ACTIVE history contains no instance from this test that is still billing; terminal records still appearing in the account instance list are expected.
  </Step>
</Steps>
